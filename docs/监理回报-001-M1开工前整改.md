## 3. §3.2 `evidenceSpanId` —— 选 (a)，补外键

```
packages/db/prisma/schema.prisma:678  evidenceSpanId   String?
packages/db/prisma/schema.prisma:679  evidenceSpan     Span?   @relation(fields: [evidenceSpanId], references: [id], onDelete: SetNull)
```

**DDL 中的外键名**：`ConceptEdge_evidenceSpanId_fkey`

```sql
ALTER TABLE "ConceptEdge" ADD CONSTRAINT "ConceptEdge_evidenceSpanId_fkey"
  FOREIGN KEY ("evidenceSpanId") REFERENCES "Span"("id") ON DELETE SET NULL ON UPDATE CASCADE;
```

**为什么不选 (b) 删字段**：`ConceptCitation` 表达的是"这个概念自身的定义出处"；
`ConceptEdge.evidenceSpanId` 表达的是"这两个概念之间**为什么**存在先修关系"。
后者是 `prereq` 节点输出 `PROPOSED` 边的依据，人工 Gate 确认时要点开的就是这一段原文。
合并进引用表会让"概念的定义出处"和"关系的推断依据"混成一份数据，且无法表达"某条边特有"。
`onDelete: SetNull`：span 被回收时边降级为无证据（仍需人工确认），不是级联删边。

## 6. §4.2 `MethodConcept` 与 `steps[].conceptIds` 漂移

**位置**：guards migration 第 235 行，视图 `v_method_concept_mismatch`。

三种不一致，一次查完：

| `mismatch` | 含义 |
| --- | --- |
| `STEP_WITHOUT_METHODCONCEPT` | 步骤里引用了，关系表没登记 |
| `METHODCONCEPT_NOT_IN_STEPS` | 关系表登记了，步骤里没引用（反向） |
| `STEP_CONCEPT_MISSING` | 步骤引用的 conceptId 在库里不存在 |

实现要点：`jsonb_array_elements ... WITH ORDINALITY` 展开 steps，
`stepOrder` 优先取 `steps[].order`（用 `~ '^[0-9]+$'` 做安全转换，脏数据不会让视图报错），
无 `order` 时退回数组下标；三种情况 `UNION ALL` 成一张表。

**构造用例与查询结果（PGlite 原样输出）**：

```
== 4.4 步骤与关系表不一致 ==
场景 A（步骤缺登记 + 登记缺步骤）：
[
  { "mismatch": "METHODCONCEPT_NOT_IN_STEPS", "methodId": "m1", "conceptId": "c3", "stepOrder": null },
  { "mismatch": "STEP_WITHOUT_METHODCONCEPT", "methodId": "m1", "conceptId": "c2", "stepOrder": 1 }
]
场景 B（步骤引用不存在的 concept）：
[
  { "mismatch": "STEP_CONCEPT_MISSING", "conceptId": "c_missing", "stepOrder": 1 }
]
```

用例构造：`m1.steps` 引用 `c1,c2`，`MethodConcept` 只有 `c1`（→ c2 缺登记），
另登记 `c3` 但步骤没引（→ 反向）；场景 B 把 steps 改成引 `c1,c_missing`。
