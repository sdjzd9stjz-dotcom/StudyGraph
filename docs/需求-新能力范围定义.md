## F · 「Skill」需要先确定语义

三种可能，实现路径完全不同：

| 方案 | 含义 | 数据模型 | 与现有规格的关系 |
| --- | --- | --- | --- |
| **F1 · MCP 工具** | 一个可被 Agent 调用的函数（如「公式推导」「代码执行」「查词」） | 无新表，工具注册在 MCP server | 与 M4 的 `MCP Server` 一致，**只扩工具清单** |
| **F2 · 指令包（Claude 式 Skill）** | 一段说明 + 可选脚本，模型按需加载作为上下文 | 新表 `Skill`（name/description/instructions/scripts/enabled/scope） | 新增；与「自建 Gateway」不冲突 |
| **F3 · 可插拔学习工具** | 面向学生的功能模块（单词卡、错题重练、公式表…） | 多半是前端模块 + 少量后端接口 | 新增 UI 负担最大 |

**我的建议：F1 + F2 组合，不做 F3。**
理由：F1 吃现成架构（M4 已有 MCP），F2 是成本最低的「扩展模型能力」方式；F3 本质是产品功能，应由里程碑逐步长出来，而不是作为「skill 系统」一次性铺开。

**需要你答**：skill 指的是哪一种？如果是 F2，还要决定「谁能装 skill」——只有内置，还是学生可自建共享。

## G · 「TapNow 的工作手段」借鉴哪一层

TapNow（Tamar AI）是「Agent 创意画布」：用聊天驱动 agent，在节点画布上编排多个模型，分步生成内容并保留中间产物。

| 可借鉴项 | 在 StudyGraph 里对应什么 | 冲突风险 |
| --- | --- | --- |
| **G1 · 对话式编排**：说一句话，agent 生成节点图草案 | 新增「编排助手」：自然语言 → 建议的节点图 | 无。但**草案必须人工确认后才落画布** |
| **G2 · 多步生成链与中间产物复用** | 已有（`Artifact` + 指纹缓存） | 无 |
| **G3 · 多模型统一调度** | 已有（LLM Gateway + 路由表） | 无 |
| **G4 · 积分/套餐计费** | `UsageRecord` 已有成本归属字段 | 商务层，非技术必需 |

**必须守住的边界**：TapNow 的核心体验是「agent 自动往下做」，而本项目的硬约束 2 是「执行必须显式触发，绝不自动重跑下游」。所以 G1 只能做成：

```
学生说需求 → 生成节点图草案（不进画布、不执行）
           → 学生确认 → 落画布（仍是 DRAFT/READY）
           → 学生点执行 → 才消耗 token
```

**任何「agent 自己连跑四步」的实现都违反硬约束，一律不做。**

**需要你答**：G 只要 G1（对话式编排），还是 G1+G4（含用量配额）？

## H · Cherry Studio API 的范围

Cherry Studio 的 API 网关对外是 **OpenAI 兼容 + Anthropic 兼容两套 HTTP API**，Bearer 鉴权，含模型列表。

### 规格里**已有**的

| 端点 | 规格位置 |
| --- | --- |
| `POST /v1/chat/completions`（OpenAI 兼容代理 + 计量 + 路由 + 前缀缓存） | 规格 §API 契约 |
| `GET /v1/providers`、`/v1/credentials`(CRUD)、`/v1/credentials/:id/test`、`/v1/model-prefs` | 规格 §BYOK |
| MCP Server（`canvas.*` / `methods.*` / `problems.*` / `papers.*` / `analytics.*`） | 规格 §MCP |
| PAT + OAuth2 scope | 规格 §鉴权 |

### 三档范围

| 档 | 内容 | 工作量估计 | 风险 |
| --- | --- | --- | --- |
| **H1 · 兼容网关（推荐）** | `/v1/models`、`/v1/chat/completions`（含 SSE 流式）、`/v1/embeddings`、Anthropic 兼容 `/v1/messages` | 小（网关与计量已具备） | 低 |
| **H2 · 网关 + 应用接口** | H1 + 供应商目录对外只读 + 知识库（上传/检索）对外 + MCP 工具清单 | 中 | 中：知识库对外要重新审一遍凭据隔离 |
| **H3 · 近乎完整复刻** | H2 + 助手、提示词库、翻译/OCR/绘图等 Cherry Studio 应用层功能 | 大，≈ 再造一个 M6 | 高：大量功能与「学习」无关，会稀释交付 |

**我的建议：H1，H2 视需要追加。**
理由：H1 才是「别的客户端能接进来」的核心，且规格已经铺好了 80%；H3 里的大半功能（绘图、OCR、翻译）与产品定位无关，做了也不加分，还会把 M2 收口继续往后推。

**需要你答**：选 H1 / H2 / H3？
