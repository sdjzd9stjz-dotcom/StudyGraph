## 1. 【P0-1】迁移作用域：三类实体各自守自己的状态机

**改法（二选一，说明理由）：**

**方案 A · 传参（推荐）** —— 把"哪些状态需要引用"作为 `TG_ARGV` 传进来：

```sql
CREATE OR REPLACE FUNCTION "studygraph_assert_citation_before_verify"()
RETURNS trigger AS $$
BEGIN
  IF NEW."status"::text = ANY (TG_ARGV[2:]) THEN
    ...
```

```sql
-- Concept / Method：两个状态都要引用
EXECUTE FUNCTION "studygraph_assert_citation_before_verify"(
  'ConceptCitation','conceptId', 'VERIFIED','PENDING_REVIEW');

-- Problem：只有 VERIFIED 要引用（PENDING 是"待三检"，REJECTED 必然不该有）
EXECUTE FUNCTION "studygraph_assert_citation_before_verify"(
```

**用 `::text` 比较，不要用枚举字面量直接比。** 这样参数化之后类型不会打架。

## 2. 【P0-2】纯标题进了 T1：「指数函数练习目录」

### 2.1 根因（`claim-support.ts:98`）


**这是我的指令写得不严。** 010 §1.3 我写的是"定义含谓词"，一个字都没提"谓词必须来自名称之外"。而且——你已经在 `:97` 加了 `DEFINITION_EQUALS_NAME` 来判断"定义就是名称"，那条规则只拦得住**完全相等**，拦不住"名称 + 几个字"。

```

条件 1：residual.length >= MIN_RESIDUAL_CHARS        （建议 6）
条件 2：PREDICATE.test(residual)                       （在 residual 上测，不是整句）
条件 3：normalizeForCompare(definition).length >= normalizeForCompare(name).length + MIN_RESIDUAL_CHARS
```

**用这三个条件同时替换掉 `:94-98` 那段。** `NAME_NOT_IN_DEFINITION` 保留（名称必须出现），`DEFINITION_EQUALS_NAME` 可以被条件 3 覆盖，但**留着不碍事，别删**——它是给人读 `reasons` 时的显式信号。

```
residual  → 练习目录（4 字）
```

条件 1 失败（4 < 6），条件 2 失败（无谓词）。**落 T3，0 张卡。** ✅

## 3. 【P0-3】巡检把「无支撑定义」放过了

### 3.1 根因（`citation-integrity.ts:88`）

```ts
const supported = classification.reasons.every(
  (reason) => reason !== 'A1_QUOTE_NOT_IN_SPAN' && reason !== 'NO_QUOTE')
```

**这一行把「定义与引文无关」也算成了 supported。** 验收 010 的实测：

```
鲸鱼是一种行星。   ← 引文逐字可查（引的是「偶数」那页），定义却毫不相干
巡检后仍为 VERIFIED
```

**这是硬约束 1 的失守口。** 我在 010 §2.2 里写"巡检发现 PENDING_REVIEW 的引文对不上原文时，照样降级"——**我只说了引文，没说定义**。你按字面实现了，于是定义这一层的校验被删掉了。

**但这不能全推给我：** 原来的 `checkConceptCitations` 用的是 `supportsDefinition()`，那是**完整判定**。你改造时把它换成"只看 A1"，等于**降低了巡检强度**——而巡检的作用恰恰是发现"写进去时对、后来对不上"的卡。**这个降级是你引入的。**

### 3.2 要求：按「验证来源」分级，而不是一刀切

不同的卡，成立的条件本来就不同：

| 卡的来源 | 成立条件 | 巡检判定 |
| --- | --- | --- |
| **自动 VERIFIED**（无复核记录） | 当时 `classifyClaim → VERIFIED` | **必须仍然 VERIFIED**（T1 三条件全过）；不满足即降级 |
| **人工 ACCEPT 的 VERIFIED**（`reviewedBy` 非空） | 人认可了这个转述 | **A1 必须过**；定义相似度不达标**不降级**，但记 `human_approved` 证据 |
| **PENDING_REVIEW** | 引文可查，等人看 | **A1 必须过**；定义不判 |

**判别依据就是 `reviewedAt` / `reviewedBy` 是否为空。** 这是 schema 里已有的字段，不用新加。

```
if (concept.reviewedBy) {
  // 人工裁决过的：只查引文
  supported = a1Passes
} else if (concept.status === 'VERIFIED') {
  // 自动核实的：必须仍是完整 T1
  supported = classification.verdict === 'VERIFIED'
} else {
  // PENDING_REVIEW：只查引文
  supported = a1Passes
}
```

**「鲸鱼是一种行星」的走法：** 它没有 `reviewedBy`，状态是 VERIFIED → 走第二支 → `classifyClaim` 返回 UNVERIFIED（`BELOW_SIMILARITY`）→ **降级**。✅

**人工 ACCEPT 过的无聊定义不会被误杀**——那正是 §3.1 表格第一支存在的理由。

### 3.3 复验

三类卡各造一张，跑完巡检贴出：

```
A. 自动 VERIFIED + 引文对 + T1 条件全过        → 保持 VERIFIED，downgraded 不含它
B. 自动 VERIFIED + 引文对 + 定义无关（鲸鱼）   → 降级 UNVERIFIED，failures 里 reason=UNSUPPORTED_DEFINITION
C. 人工 ACCEPT + 引文对 + 定义是合理转述       → 保持 VERIFIED
D. 人工 ACCEPT + 引文伪造                       → 降级 UNVERIFIED，reason=TEXT_MISMATCH 或 A1
E. PENDING_REVIEW + 引文对                      → 保持 PENDING_REVIEW
F. PENDING_REVIEW + 引文伪造                    → 降级 UNVERIFIED
```

**六行都要有。** 少一行我就当没验。

## 4. 【P1】人工裁决的三个洞

### 4.1 重跑会把「已拒绝」重新打开

验收 010 §4 的实测：

```
连续函数  before UNVERIFIED  after PENDING_REVIEW  reviewedBy teacher  cards 1
```

**一个人明确拒绝了的卡，CARD 重跑一次就变回待审，复核人还挂着。** 这等于复核白做。

**根因：** `card.ts:60` 的保守分支只处理了 `current.status !== 'UNVERIFIED'` 的情况，而 REJECT 的结果恰好就是 `UNVERIFIED`——**拒绝后的状态和"从没审过"在数据库里长得一模一样。**

**要求：** 用 `reviewedAt` / `reviewedBy` 区分这两者。

```
若 current.status === 'UNVERIFIED' 且 current.reviewedBy 非空：
  → 说明这是被人工拒绝过的
  → 重跑时【不得】把它改回 PENDING_REVIEW/VERIFIED
  → 记 skipped，reason = 'REJECTED_BY_REVIEWER'
  → 除非：证据本身变了（不同 spanId 或不同 quote）——此时按"新证据"处理，
         清空 reviewedBy/reviewedAt，重新走分类
```

**"证据变了"的判定要写死：** `spanId` 不同 **或** `citation.quote` 不同。**不许用"定义文本变了"当理由**——定义变了但引的是同一句，那还是同一条证据。

### 4.2 并发两个裁决都成功

验收原文：

```
并发 ACCEPT 与 REJECT 均为 200
```

后写的覆盖先写的，**两个人同时裁决，谁最后提交谁赢，没有任何提示**。

**根因：** `review.ts:55` 是"先读、再判、后写"三步，中间没有原子性。

**要求：** 把状态检查做成写入条件（compare-and-set）：

```ts
const result = await prisma.concept.updateMany({
  where: { id, status: 'PENDING_REVIEW' },
  data,
})
if (result.count === 0) throw new AppError(409, 'CONFLICT', '该条目已被他人复核', { id })
```

**`updateMany` 返回 `count: 0` 就是竞争失败 → 409。** 不要用事务里再 `findUnique` 一次，那还是有窗口。

### 4.3 非法 `decision` 返回 500

`bodySchema.parse` 抛出的 `ZodError` 落进了通用错误处理。

**要求：** 在全局错误处理里加一条：`ZodError → 400 VALIDATION_FAILED`，附 `issues`。**这是全项目统一的行为**，不只这一条路由。畸形 JSON 另给错误码（`400 INVALID_JSON`），不要混。

验收方在 §6 指出路由前缀是 `/v1` 不是我指令里写的 `/api`——**以项目为准，文档里写对就行。**

## 7. 【P1】EXTRACT 提示词要求 definition === quote

验收 010 §6 提了一条我没想到的：

> EXTRACT 提示词仍要求 definition 和 quote 填同一句原文（`extract.ts:26`）。遵照提示的模型不会主动产出转述。这会影响 T2 样本来源。

**这一条很重要。** 看 `extract.ts:26`：

```
'3. definition 和 quote 均填同一句完整原文，句中须有概念名称及解释。'
```

**提示词逼着模型把定义抄成引文**，所以 T1 全是"逐字"，T2 永远产不出来——**三档设计在源头就被堵死了**。

### 7.1 要求

改成分离的两个字段：

```
3. quote：必须是原文中【逐字连续】的一句话，不得改写、不得拼接。
4. definition：用你自己的话说明这个概念是什么，必须包含概念名称；
   不得引入原文之外的信息。允许与 quote 措辞不同，但语义必须一致。
```

**并且：**

- `promptVersion` 会随之变化——**这是对的，别想着固定它**
- 改完之后**必须重跑**，否则 T2 分布还是假的
- 提示词改动要写进 `docs/architecture.md` 或对应里程碑文档

### 7.2 一个反向风险，提醒你

提示词改了之后，**模型可能被诱导去编造**（"用你自己的话"→ 加戏）。所以 §2 的谓词规则和 §3 的巡检必须**先修好再重跑**，否则新一批数据会比旧一批更脏。

**顺序不能颠倒。**
