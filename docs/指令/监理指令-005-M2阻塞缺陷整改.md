## 2. 逐项整改要求

### A ·【P0】原文变更后旧引用仍通过 —— 硬约束 1

**现象（E05 原文）：**

```
initial {"ok":true}
changed {"ok":true} fresh TEXT_MISMATCH
negative {"ok":true}
```

页文本从 `abc` 变为 `xyz`，`resolver.verify(span)` 仍返回 `{ok:true}`；同一时刻用 `verifySpan` 直接校验（无缓存）则正确返回 `TEXT_MISMATCH`。

**根因方向：** 缓存条目只按 `(sourceId, page)` 组织，没有绑定原文版本。原文变了，缓存键没变。

**要求：**

1. 校验缓存的键**必须包含原文版本**。可用的现成字段：`Source.checksum`（M1 已落库）或页文本自身的哈希。
2. 或者：缓存条目在写入时记录当时的页文本哈希，读取时比对，不一致即失效。
3. **两种做法都行，但必须满足这条可观察行为：同一 span，原文变更后第二次校验必须失败。**

**复验命令（用 E05 同一条）：**

```powershell
node --input-type=module -e "import {verifySpan,createSpanResolver} from './apps/api/src/spans/resolver.ts'; let page='abc'; const span={id:'s',sourceId:'doc',page:1,charStart:0,charEnd:1,text:'a'}; const resolver=createSpanResolver({loadSpan:async()=>span,loadPageText:async()=>page}); console.log('initial',JSON.stringify(await resolver.verify(span)));page='xyz';console.log('changed',JSON.stringify(await resolver.verify(span)),'fresh',verifySpan(span,new Map([[1,page]])).reason)"
```

**必须输出：**

```
initial {"ok":true}
changed {"ok":false,...} fresh TEXT_MISMATCH
```

`changed` 那一行**只要还是 `ok:true`，A 项就没有关闭。**

**附加要求（这条比修复本身更重要）：**

修好之后，**再用真实卡片验证一次拦截**：构造一张已落库的卡 → 改动其引用的原文 → 重新校验 → 该卡必须降级为 `UNVERIFIED`。E05 只是组件级，规格验收要看的是数据层行为。

### C ·【P1】registry 自检漏检

**现象（E07）：**

```
missingPlan true 0 true
```

删掉 `PLANNED_PLAN.SOURCE` 后，`selfCheck()` 仍返回 `ok:true`、`problems.length === 0`，且 `planned` 里依然含 `SOURCE`。

**根因方向：** 自检没有拿「已实现集合 ∪ 计划集合」去和 `NodeType` 的 17 个值做**双向差集**。它可能在检查自己内部一致性，而不是检查与规格的一致性。

**要求：**

1. `selfCheck()` 必须计算：
   - `implemented ∪ planned` 与 `NODE_TYPES`（17 个）的差集
   - `implemented ∩ planned` 是否为空（同一 type 不能既实现又计划）
2. 缺任何一个 → `ok:false`，`problems` 里写明缺哪个 type
3. **启动路径必须调用 `selfCheck()`**，不通过时启动失败并打印原因

**复验命令（用 E07 同一条）：**

```powershell
node --input-type=module -e "import {PLANNED_PLAN,selfCheck} from './apps/api/src/nodes/registry.ts'; delete PLANNED_PLAN.SOURCE; const r=selfCheck();console.log('missingPlan',r.ok,r.problems.length,r.planned.includes('SOURCE'))"
rg -l 'selfCheck\(' apps/api/src
```

**必须输出：**

- `missingPlan false 1 false`（`ok` 为 false，至少有 1 个 problem，`planned` 里不再有 SOURCE）
- `rg` 的结果**必须包含 `server.ts` 或 `app.ts`**，不能只有 `registry.ts`

### D ·【P1】适配器凭空生成计量与模型版本

**现象（E06）：**

```
extract {"data":{},"usage":{"tokensIn":0,"tokensOut":0,"cachedTokens":0},"modelVersion":"gpt-4o-mini"}
method  {"data":{},"usage":{"tokensIn":0,"tokensOut":0,"cachedTokens":0},"modelVersion":"claude-sonnet-4-5"}
```

给的响应体里**没有 `usage`、没有 `model`**，适配器却返回了全 0 的用量，并把 `modelVersion` 回退成了**请求时写的别名**。

**为什么这是 P1 而不是 P2：**

- `usage` 全 0 → 额度计量失效，学生不知道花了多少
- `modelVersion` 用别名 → 指纹里的 `modelVersion` 字段失去意义（同一别名背后可能换模型），**M2 的缓存正确性直接建立在它上面**
- 「缺字段当成功」是本项目明令禁止的静默降级

**要求：**

1. 适配器**必须校验**响应中的 `usage` 与 `model`：
   - 缺失、为 null、类型不对、数值为负 → 抛错，不得返回
   - 错误码建议 `PROVIDER_RESPONSE_INVALID`，`details` 里带 `{ provider, missing: ['usage'] }`
2. `modelVersion` **只能取自响应体的 `model` 字段**。响应没有 → 报错，不许回退到请求别名。
3. 数字 0 是合法值（某些缓存命中场景），但**"字段不存在"与"值为 0"必须区分**。

**复验命令（用 E06 同一条）：**

```powershell
node --input-type=module -e "import {createGateway} from './apps/api/src/llm/gateway.ts'; for(const [taskType,payload] of [['extract',{choices:[{message:{content:'{}'}}]}],['method',{content:[{type:'tool_use',input:{}}]}]]) { const gw=createGateway({resolveApiKey:async()=>'test',fetchImpl:async()=>Response.json(payload)}); try{console.log(taskType,JSON.stringify(await gw.complete({taskType,messages:[],user:{id:'audit'}})))}catch(e){console.log(taskType,'THREW',e.code??e.message)} }"
```

**必须输出：** 两行都是 `THREW PROVIDER_RESPONSE_INVALID`（或等价错误码），**不能有任何一行打印出 usage 或 modelVersion**。

**另需补一条正向用例：** 响应体里 `usage` 与 `model` **齐全**时，返回的 `modelVersion` 必须等于响应里的 `model` 值，`tokensIn/Out` 等于响应里的数——不许被别名覆盖。

### E ·【P1】前缀键被丢弃；BYOK 无调用方

**现象：**

- E09：只改 `cachePrefixKey`（`source:1:v1` → `source:1:v2`），两次出站请求体**完全相同**（`sameRequest true`）
- E16：`rg -l 'decryptSecret|providerCredential\.' apps/api/src` 只命中 `llm/byok.ts` 自己 —— **解密函数在生产代码里没有调用方**

**规格依据：** 「教材原文做 system 前缀可实现前缀缓存，省 60%+ 成本」+「BYOK：学生自带的 key 走 `ProviderCredential` 表」。

**要求：**

1. **`cachePrefixKey` 必须真的影响出站请求。** 可观察标准：两个不同的前缀键 → 两次出站请求体**不同**。
   - 具体怎么用（system 前缀、`cache_control` 块、`prompt_cache_key` 之类）由你按各厂商能力定，写进 `docs/architecture.md`
2. **BYOK 必须接线：**
   - `resolveApiKey` 的签名要能拿到**用户身份**（现在只收 `provider`）
   - 生产路径：按 `(userId, provider)` 查 `ProviderCredential` → `byok.ts` 解密 → 使用
   - 用户无凭据时回退到环境变量；两者都没有 → 抛错（**不许用一个假 key 继续跑**）
3. `ProviderCredential` 里存的是密文，**解密后只在内存中存活，不写日志、不进错误信息**

**复验命令：**

```powershell
# 前缀键必须影响请求体
node --input-type=module -e "import {createGateway} from './apps/api/src/llm/gateway.ts';const requests=[];const g=createGateway({resolveApiKey:async()=>'test',fetchImpl:async(u,o)=>{requests.push(o.body);return Response.json({choices:[{message:{content:'{}'}}],model:'snapshot',usage:{prompt_tokens:1,completion_tokens:1}})}});for(const key of ['source:1:v1','source:1:v2'])await g.complete({taskType:'extract',messages:[],user:{id:'audit'},cachePrefixKey:key});console.log('sameRequest',requests[0]===requests[1])"

# BYOK 必须有生产调用方
rg -l 'decryptSecret|providerCredential\.' apps/api/src
```

**必须输出：**

- `sameRequest false`
- `rg` 的结果**至少包含一个非 `byok.ts` 的文件**（gateway 或 routes 层）

**并且要用两个用户验证**：用户 A 配了 key、用户 B 没配，两次调用使用的密钥不同（可在 adapter 里打点，但**不许打明文**）。

### F ·【P1】数据库不可达时漂移护栏假通过

**现象（E13）：**

```
Error: P1001
Can't reach database server at `localhost:5432`
...
✅ 无漂移（schema 与库一致，手写索引未被触碰）
```

连不上库，却报告"无漂移"并退出 0。

**为什么严重：** 这是**护栏本身的静默降级**。CI 里一跑，看着是绿的，实际上什么都没查。而且这个脚本存在的唯一理由就是防止索引被误删——它失效时最危险。

**要求：**

1. `migrate diff` 子进程非零退出时，**脚本必须非零退出**，并打印"无法连接数据库，漂移未检测"
2. 区分三种情况，各有明确退出码：

| 情况 | 退出码 | 输出 |
| --- | --- | --- |
| 数据库不可达 | **2** | `❌ 无法连接数据库，漂移未检测` |
| 连上且无漂移 | 0 | `✅ 无漂移` |
| 连上且检出受保护索引的 DROP | 1 | 现有的红字说明 |

3. 不许用"stderr 里有没有 Error 字样"这种启发式判断——**看子进程的退出码**。

**复验（三个场景都要跑）：**

```powershell
# 场景 1：库不可达（临时改 DATABASE_URL 指向不存在的端口）
$env:DATABASE_URL='postgresql://x:x@localhost:5999/nope'; node scripts/check-drift.mjs; Write-Output "exit=$LASTEXITCODE"
# 场景 2：正常 → exit=0
# 场景 3：受保护索引存在 → exit=1（当前就是此状态）
```

**场景 1 必须输出 `exit=2`，且**不能出现"✅"字样**。

### G ·【P2】三项小问题

**G1 · span 接受负偏移（E05：`negative {"ok":true}`）**

- `charStart < 0`、`charEnd < 0`、`charEnd <= charStart` 都必须在**纯函数层**拒绝，不能只靠 Zod 在 HTTP 层兜
- 错误原因用 `BAD_RANGE`，与 `TEXT_MISMATCH` 区分开
- 复验：E05 的 `negative` 那一行必须变成 `{"ok":false,...}`

**G2 · 非法 JSON 返回 500（E12）**

```
{"error":{"code":"INTERNAL_ERROR","message":"服务器内部错误"}} HTTP500
```

客户端发了坏 JSON，服务器不该报 500。要求：

- 返回 **400**，错误码 `INVALID_JSON`，`details` 里带偏移量或简短原因
- 同时确认：空 body 的执行接口仍要返回 501（不要为了修这个把 501 行为改掉）
- 复验：
```powershell
curl.exe -sS -X POST http://127.0.0.1:3001/v1/canvases -H 'Content-Type: application/json' --data-binary '{' -w ' HTTP%{http_code}'
```
必须 `HTTP400` 且 `code=INVALID_JSON`

**G3 · S3 容器没有健康状态（E01：`s3 Up 42 minutes` 无 healthy）**

- 给 S3 服务加 `healthcheck`，让 `docker compose ps` 显示 `(healthy)`
- 健康检查要**真的探测服务**，不能 `exit 0` 敷衍
- 复验：`docker compose ps --format '{{.Service}} {{.Status}}'` 三个服务**都带 `(healthy)`**

## 3. 自主决策裁决：保留 SeaweedFS

验收方把 S3 实现选型提给我裁决（§6、§7③）。**裁决：保留 SeaweedFS。**

**理由：**

1. 规格原文是「S3 兼容存储」，没有点名厂商。SeaweedFS 满足要求，且 E02 已证明读写删往返正确（65536 字节、sha256 一致、删除后读回失败）。
2. 换回 MinIO 需要重建容器、重跑往返测试，**收益为零**。
3. 代码走 `S3_ENDPOINT` 配置，换别的 S3 兼容实现不用改代码——这一点必须保持。

**但有两项附加要求：**

- 加健康检查（见 G3）
- 在 `docs/architecture.md` 新增一节「对象存储选型」，写明：选了 SeaweedFS、为什么它可以、`S3_ENDPOINT` 保持可替换、健康检查的标准是什么

**SG-SUP-004 §3.1 里我写的 `docker compose up -d redis minio` 就此作废**，以本指令为准：**服务名是 `s3`，镜像自定，唯一硬要求是三个服务都 healthy。**
