## 1. 裁决：A 方案的三层口径

### 1.1 现状为什么只有 7 条

看 `apps/api/src/spans/claim-support.ts:4`：

```ts
if (!quote || !name.trim() || definition.trim() !== quote || !spanText.includes(quote)) return false
```

**这一行要求 `definition` 与 `quote` 逐字节相等。** 不是"定义与原文逐字相等"——是**抽出来的定义必须和引文一模一样**。

再看 `013` 的观察：22 字/页的 PPT，老师写「连续函数：在区间上每一点都连续」，模型抽出来必然是「在区间上每一点都连续的函数称为连续函数」。**两者都忠实于原文，但字面不同。** 那条规则必然把它们全拦下。

所以不是我判断错了，也不是你偷工——**是这条规则把"引文可信"和"定义可读"两件事绑成了一个布尔值。**

### 1.2 拆成两个独立判定

方案 A 的核心是**把一条断言拆成两条**：

| 判定 | 问的问题 | 能不能机械验 | 失败意味着什么 |
| --- | --- | --- | --- |
| **A1 · 引文在不在原文里** | `quote` 是否逐字出现在 span 原文中 | ✅ 能，精确比对 | 引文是编的 → **造假，必须拒** |
| **A2 · 定义是不是这条引文的合理转述** | `definition` 是否由 `quote` 支撑 | ⚠️ 只能近似 | 语义可能对，也可能错 → **需要人** |

**这两件事的严重性差一个数量级。** A1 失败是硬失败，A2 失败是待审。

现在的代码把 A1 和 A2 合并进一个 `definition.trim() !== quote`，导致 A1 的严格性被 A2 的不确定性拖垮——**一条规则，两个目标，必然两头都不对。**

### 1.3 三档判决表

`card` 与 `extract` 共用同一个分类器，**不许两处各写一套**：

| 档位 | 条件（全部满足才进入该档，从上往下判） | 结果 |
| --- | --- | --- |
| **T1 · 逐字** | A1 通过 且 `definition.trim() === quote` 且 名称在定义中 且 定义含谓词 | **`VERIFIED`** |
| **T2 · 转述** | A1 通过 且 名称在定义中 且 定义含谓词 且 相似度达阈值 | **`PENDING_REVIEW`** |
| **T3 · 无支撑** | 其余一切（含 A1 失败、无 quote、无 span、纯标题） | **`UNVERIFIED`**，不产卡 |

**关键：T2 里的 A1 必须通过。** `PENDING_REVIEW` 的引文也是逐字可查的——它只是"定义的措辞是人写的，不是原文抄的"。**引文凡是编的，一律进 T3，没有例外。**

### 1.4 T2 的"相似度"怎么定（这是唯一需要调参数的地方）

**不要用"模型说我等价"当判据。** 那是自己出题自己答。

用**字符 bigram Jaccard 相似度**，纯机械、可复现、无模型参与：

```
X = 去空白去标点后的 quote 的字符 bigram 集合
Y = 去空白去标点后的 definition 的字符 bigram 集合
J = |X ∩ Y| / |X ∪ Y|

T2 条件：J ≥ REVIEW_MIN_BIGRAM_SIMILARITY  且  0.5 ≤ len(definition)/len(quote) ≤ 2.0
```

**初值给 `0.45`，写进 `packages/contracts/src/thresholds.ts`。** 但我要求你做一件更重要的事——

### 1.5 阈值必须用那 20 条真实被拒数据校准，不许拍脑袋

**这是本轮最容易糊弄过去、也最容易留下隐患的一步。**

用现有的 27 条候选 claim（013 的账本里应该有全量），跑一遍分类器，出一张 **27 行的表**：

| claim 序号 | name | quote 是否在原文(A1) | J 值 | 定义长度比 | 判到哪档 |
| --- | --- | --- | --- | --- | --- |

然后给出**判定分布**：

```
T1 = ? 条
T2 = ? 条
T3 = ? 条
T3 里因 A1 失败（引文造假）= ? 条   ← 这个数必须是 0 或极少，否则问题比数量更严重
```

**校准要求：**

- 若 `0.45` 把明显是转述的内容判进 T3，说明偏严，**可以下调，但必须说明下调到多少、为什么这个值仍然拦得住"引用别处内容冒充本页"**
- 若 `0.45` 把风马牛不相及的内容判进 T2，说明偏松，**必须上调**
- **`REVIEW_MIN_BIGRAM_SIMILARITY` 一旦定下，写进 thresholds.ts 并附校准表在报告里**，以后改它要说明理由

### 1.6 数量口径：怎么算"够不够"

| 指标 | 目标 | 下限 |
| --- | --- | --- |
| `VERIFIED`（T1）| **≥ 15** | **≥ 10** |
| `PENDING_REVIEW`（T2）| 不设目标 | 不设下限 |
| **`VERIFIED + PENDING_REVIEW`** | **≥ 15** | **≥ 10** |

**两条都要报。** 只报合计不报 `VERIFIED` 单独的数，视为未完成——因为我要看**有多少是真逐字、多少是等人看的**。

**如果合计仍不到 10**：不要凑。立刻停手，把 §1.5 的分类表、以及"这 20 条各自卡在哪个条件上"的统计交上来。**那说明这份材料的上限确实低，我们走方案 C，但那是用户拍板的事，不是你放宽阈值能解决的。**

## 2. A 方案的施工要求

### 2.1 数据库：加枚举值，但**必须拆成两个 migration**

Prisma 的 `ALTER TYPE ... ADD VALUE` 在同一个事务里加值并使用，**PostgreSQL 会报 `unsafe use of new value`**。这是硬限制，不是配置问题。

**migration 1**（只加值，不引用）：

```sql
ALTER TYPE "VerificationStatus" ADD VALUE IF NOT EXISTS 'PENDING_REVIEW' BEFORE 'MERGED';
```

**migration 2**（用值）：触发器、视图、降级逻辑的改动。

**两个 migration 之间必须重新生成 Prisma Client。** 顺序错了会报"枚举值不在类型里"，不要试图用 `as any` 绕。

### 2.2 触发器：`PENDING_REVIEW` 也必须有引用

现有触发器在 `migrations/20261118030100_guards/migration.sql:84`：

```sql
IF NEW."status" = 'VERIFIED' THEN
```

**这里必须改成：**

```sql
IF NEW."status" IN ('VERIFIED', 'PENDING_REVIEW') THEN
```

**为什么这是 P0 级的要求：** `PENDING_REVIEW` 的**唯一合法性来源**是"引文在原文里查得到"。如果允许无引用的 `PENDING_REVIEW` 存在，这个状态就退化成了"随便标个待审都能进库"，**比直接标 VERIFIED 更危险**——因为它看起来像是被审核过。

**同时改三处下游：**

| 位置 | 现在的写法 | 必须改成 |
| --- | --- | --- |
| `guards/migration.sql:143` 删引用时的降级 | `WHERE "status" = 'VERIFIED'` | `WHERE "status" IN ('VERIFIED','PENDING_REVIEW')` |
| `guards/migration.sql:198` `v_verified_without_citation` 视图 | `c."status" = 'VERIFIED'` | 同上（含 Method / Problem） |
| `citation-integrity.ts:43` 巡检查询 | `where: { status: 'VERIFIED' }` | `status: { in: ['VERIFIED','PENDING_REVIEW'] }` |

**第三处特别重要：** 漂移巡检只查 `VERIFIED` 的话，`PENDING_REVIEW` 的卡**永远没人复查**。它挂着"待审"两个字，实际是无人区。改完之后，巡检发现 `PENDING_REVIEW` 的引文对不上原文时，**照样降级到 `UNVERIFIED`**。

### 2.3 契约层：三处同步

| 文件 | 改动 |
| --- | --- |
| `packages/contracts/src/artifacts/concept-claims.ts:16` | `z.enum(['VERIFIED','UNVERIFIED'])` → 加 `'PENDING_REVIEW'` |
| 同文件 `superRefine` | 约束从"VERIFIED 必须有 spanId"扩到 **"非 UNVERIFIED 必须有 spanId"** |
| `packages/contracts/src/thresholds.ts` | 新增 `REVIEW_MIN_BIGRAM_SIMILARITY` 与 `REVIEW_MAX_LENGTH_RATIO` |

### 2.4 分类器：一个函数，两处调用

**现状：** `extract.ts:167` 用 `claim.verified ? 'VERIFIED' : 'UNVERIFIED'` 写状态；`card.ts:36` 又判一次 `claim.status !== 'VERIFIED'`。

**要求：**

1. 把 `supportsDefinition()` 改造为**返回三档**的分类器，比如：

```ts
export type ClaimVerdict = 'VERIFIED' | 'PENDING_REVIEW' | 'UNVERIFIED'
export function classifyClaim(input: {
  name: string; definition: string; quote?: string; spanText: string
}): { verdict: ClaimVerdict; reasons: string[] }
```

2. `reasons` 必须是**可读的失败原因清单**（`A1_QUOTE_NOT_IN_SPAN` / `NAME_NOT_IN_DEFINITION` / `NO_PREDICATE` / `BELOW_SIMILARITY` / `LENGTH_RATIO_OUT_OF_RANGE`）。**不许只返回一个布尔值**——013 里那 20 条被拒的 claim，你只能笼统说"标题、自述与原文不逐字相等"，就是因为没有 `reasons`。

3. `extract` 写状态、`card` 建卡，**都必须调这一个函数**。`card.ts:36` 的过滤条件改成 `verdict === 'UNVERIFIED'` 才跳过。

### 2.5 人的复核入口（M2 不做 UI，但接口要有）

**没有复核入口，`PENDING_REVIEW` 就是一个永远不进不退的死状态。** 这会变成一个比 7 张卡更难解释的问题。

M2 阶段的最小要求：

- 一个 `POST /api/concepts/:id/review` 接口，body `{ decision: 'ACCEPT' | 'REJECT', reviewerUserId, note? }`
- `ACCEPT` → `VERIFIED`；`REJECT` → `UNVERIFIED`
- 记录 `reviewedAt` / `reviewedBy`
- **必须校验 reviewer 有该画布的编辑权限**（复用 M1 的 `CanvasRole`）
- **不许提供批量接口**——批量通过就是把"人工复核"变成"一键放行"

**schema 加两个字段即可**（这是 migration 2 的一部分）：

```prisma
model Concept {
  reviewedAt DateTime?
  reviewedBy String?
}
```

Method 同样处理（M2 里 Method 还没产出，但枚举是共享的，**一并改，不要留个半残的状态**）。

### 2.6 前端展示口径（M2 只做后端，M5 之前不接）

`PENDING_REVIEW` 的卡**不进学生视图**。它是教师侧"待审队列"的素材。**M2 阶段的前端溯源抽屉里，如果展示卡，必须能区分这三种状态**，不能把 `PENDING_REVIEW` 画成和 `VERIFIED` 一样的绿勾。
