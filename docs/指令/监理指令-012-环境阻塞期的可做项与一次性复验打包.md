## 2. 【P1】产物不完整，导致校准永远无法回溯

### 2.1 这一条是 011 回报里暴露出来的真缺陷

你写：

> 原因：需要 DB（**旧 claim 的 quote 在旧产物里被丢掉了**）+ 有效 key（重抽）。

**"旧 claim 的 quote 被丢掉了"——这不是校准做不了的原因，这是一条独立缺陷。**

`quote` 是判定的核心输入之一：A1 判它、bigram 相似度算它、长度比用它。**一次执行跑完了，产物里却没有留判定所需的输入**，意味着：

- 当时那 7 张卡为什么过、20 条为什么没过，**事后无法复核**
- 阈值从 0.45 调到别的值，**无法在这批数据上重放**
- 验收方说"27 条仅 7 条保留引文计数"——这不是巧合，是产物设计漏了字段

**这跟 A 项、008 指纹是同一类错误的第三次出现：** 把"结果"存下来了，把"判定依据"丢了。结果看起来对，但你永远证明不了它对。

### 2.2 要求

**任何一次 `extract` 执行的产物，必须自带完整的判定输入快照，脱离数据库也能重放分类。**

最少要包含每条候选的：

```json
{
  "name": "...",
  "definition": "...",
  "quote": "...",
  "spanIds": ["..."],
  "spanText": "...",          ← 关键：判定时的原文，不是事后去查
  "reasons": [...],
  "verdict": "...",
  "similarity": 0.0,
  "lengthRatio": 0.0,
  "promptVersion": "...",
  "classifierVersion": "..."   ← 见 §2.4
}
```

**`spanText` 也要存**：span 可能被后续操作改掉或删掉，但"当时判定用的那段原文"必须留住。否则巡检和重放会用到两份不同的数据。

**存放位置：** 随 artifacts 一起，落在对象存储或 `Run` 的产物 JSON 里。**不要只存 verdict 和 similarity**——那还是"结果"，不是"依据"。

### 2.3 校准因此可以离线做

**修完之后，校准表不需要 DB、不需要 key。** 只要产物里有那 27 条的完整快照：

```bash
node scripts/replay-calibration.mjs <artifact.json>
# 输出 27 行表，不连库、不调模型
```

**这是本轮最有价值的一件事：把"必须等环境"的一个环节，变成"随时可做"。**

**先做一件事再动手：** 翻一下 013 的账本 JSONL，看里面到底留了什么字段。三种情况：

| 情况 | 处置 |
| --- | --- |
| 27 条都有完整 quote + definition + spanText | 立刻离线跑校准，本轮就能交表 |
| 只有部分字段 | 说明丢了哪些，能重放多少条就放多少条，**明确标注"基于 N/27"** |
| 只有 verdict 和计数 | 确认丢失，写进回报；**这批校准作废，等重抽**，不要拿新批次冒充 |

**第三种情况不要硬凑。** 新批次单独列表，与 013 分开。

### 2.4 `classifierVersion`

分类器改了（011 的 residual 规则、阈值），旧产物就该知道自己是用哪版判的。

```ts
export const CLASSIFIER_VERSION =
  sha256(【规范化后的判定规则源码】).slice(0, 12)
```

要求：**规则一改，这个值就变**，写进产物。这样"这批数据是旧规则判的"能一眼看出来，而不是靠人记。

**自测：** 改一个阈值常量，`CLASSIFIER_VERSION` 必须变。这条要进单测。

## 3. 【P1】包级类型检查：单文件过不等于包过

### 3.1 你自己提了

> `apps/api` 没有自己的 `tsconfig.json`，所以这是单文件严格检查，不是"整个 api 包 tsc"。

**这个自陈是对的，也暴露了 §5 关闭条件的口径太松。** 我在 011 §5.3 只写了"review.ts 必须 0 error"，你就只检查了 review.ts。

**单文件检查通过，包里有 40 个错，评审照样绿。** 这跟"用身份代替内容做判定"是同一个毛病。

### 3.2 要求

**补 `apps/api/tsconfig.json`**，继承 `tsconfig.base.json`，覆盖 `src/**/*.ts`，然后：

```bash
tsc -p apps/api/tsconfig.json --noEmit

```

**补的过程如果暴露出大量既有类型错误**（很可能），**不要一次全修，也不要关严格选项**。做法：

1. 先补配置，跑一次，**把完整错误清单贴进回报**
2. 分两堆：本轮改动引入的（**必须清零**）/ 历史遗留的（列出，排期）
3. 历史遗留的**不许用 `@ts-ignore` 静默**——要 `@ts-expect-error` 且带理由注释，或者列成待修清单

**`skipLibCheck: true` 可以有，`strict: false` 不许。** 降严格度换绿灯，等于把这条检查废掉。

## 5. 【P1】promptVersion 变了，那 7 张旧卡怎么办

### 5.1 问题

你写：

> `promptVersion` 随之变化（没有固定它），所以旧产物会因指纹失配而自然淘汰。

**产物会被淘汰，但数据库里那 7 张 `VERIFIED` 的卡不会。** 它们是**旧提示词**（definition 必须等于 quote）产出的。新规则下：

- 它们大概率仍然是 T1（定义确实等于引文），**分类不会变**
- 但它们**永远不可能产出 T2**，所以"新规则下的 T2 分布"跟这 7 张无关
- 更麻烦的是：如果有人拿"库里已有 7 张 VERIFIED"去凑 010 §1.6 的下限，**那是跨规则混数**

### 5.2 要求

**重跑时用一个全新画布，旧画布保留作历史对照。** 我 011 里没写清楚，现在补上：

| 画布 | 用途 |
| --- | --- |
| 旧画布 `cmwnn9tpg0001q52wfgghlljt` | **冻结**，作为 013 的历史证据，不再写入 |
| 新画布 | 011 之后所有产出的唯一来源 |

**数量统计只能来自新画布。** 报告里如果出现"7 + 18 = 25 张"，直接判数据造假。

**并且**：新画布的卡要带上 `classifierVersion` 和 `promptVersion`，**在回报里列出 3 张卡的这两个值**，证明它们出自新规则。
