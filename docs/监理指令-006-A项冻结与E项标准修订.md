## 1. A 项 · 第二次驳回（P0，已冻结）

### 1.1 剩余的两个反例

**反例一：改引文文本，缓存放行**

```
pageHash initial true changedQuote true
```

span 是 `{id:'s', page:1, sourceId:'src', charStart:0, charEnd:1, text:'a'}`：

1. `verify(s)` → `true`（正确，页文本 `abc[0,1) === 'a'`）
2. `verify({...s, text:'z'})` → **`true`**（错误，`'a' !== 'z'`）

**根因：** 缓存键是 `(id, page, charStart, charEnd)`，**不含期望文本**。而 `verifySpan` 的判定恰恰是 `pageText.slice(start,end) === span.text`——结果依赖 `span.text`，但 `span.text` 不在复用条件里。

这意味着：只要 span 的 id 和区间不变，**你给它什么期望文本它都说对**。缓存实质上把校验函数变成了恒真函数。

**反例二：取不到版本号时，把 `undefined` 当稳定版本**

```
missingVersion initial true changedQuote true
missingVersion changedPage {"ok":true} negative BAD_RANGE
```

`loadSourceVersion` 返回 `undefined` 时，页文本从 `abc` 改成 `xyz`，`verify` 仍返回 `{"ok":true}`。

**根因：** `undefined` 被当成了一个合法的、稳定的版本值参与缓存判定。取不到版本，就等于**无法判断缓存是否仍然有效**，此时正确行为只有一个：**回退到直接比对页文本**。

**这两条是同一个思维定式的两面：** 都假设"缓存命中 = 可以跳过校验"，而正确的假设是"缓存命中 = 可以跳过**读页文本**，但不能跳过**与该 span 自身相关的判定**"。

### 1.2 修复要求

**缓存复用条件必须覆盖判定函数的所有输入。** 判定函数是：

```
verify(span, pageText) = ok  iff  span.charStart >= 0
                          ∧ span.charEnd > span.charStart
                          ∧ pageText.slice(span.charStart, span.charEnd) === span.text
```

所以缓存键至少要包含：

| 必须纳入 | 理由 |
| --- | --- |
| `sourceId` | 换来源，原文不同 |
| `page` | 换页，原文不同 |
| `charStart` / `charEnd` | 区间不同，切片不同 |
| **`span.text` 的哈希（或全文）** | **反例一**：期望文本变了，结论就该变 |
| **页文本版本（`Source.checksum` 或页哈希）** | 反例二的反面：版本变了必须失效 |

**取不到版本时的行为（反例二）：**

```
loadSourceVersion() → undefined
  ⟹ 不得使用缓存
  ⟹ 必须读页文本并重新比对
  ⟹ 若比对失败，返回 TEXT_MISMATCH（不是 true）
```

`undefined` **绝不可以**被当作"版本未变化"。

### 1.3 复验命令（用验收方那一条，一字不改）

```powershell

**关闭条件（四行，逐行比对）：**

```

## 2. C 项 · P1 未关闭

### 2.1 现象

```
baseline true
extra true []          ← 加入 OUTSIDE（不在 17 个 type 里）后，自检仍通过
missing false ["SOURCE 既未实现也没有计划里程碑"]
```

`missing` 分支修好了（删掉计划会报错），但 **`extra` 分支没修**——往 `PLANNED_PLAN` 里塞一个不存在的 type，自检视而不见。

**根因：** 构造计划集合时，先按 `NODE_TYPES` 过滤了键，然后再比对。过滤之后剩下的当然天然属于 17 个 type，**多出来的被过滤掉了，永远不会报错**。

### 2.2 修复要求

**对原始键集合检错，不要先过滤。**

自检必须计算三类问题：

| 类型 | 判定 | 报错文案要求 |
| --- | --- | --- |
| **遗漏** | `NODE_TYPES - (implemented ∪ planned)` 非空 | 点名缺哪个 type |
| **多余** | `(implemented ∪ planned) - NODE_TYPES` 非空 | **点名多余的键叫什么** |
| **重叠** | `implemented ∩ planned` 非空 | 点名哪个 type 既实现又计划 |

三类任一非空 → `ok: false`，`problems` 里逐条列出。

**`extra` 的报错文案要能让读日志的人立刻明白**，例如：

```
"OUTSIDE 不是 NODE_TYPES 中的节点类型（可能是拼写错误，或计划表被改坏了）"
```

### 2.3 复验命令

```powershell
node --input-type=module -e "import {PLANNED_PLAN as p,selfCheck as c} from './apps/api/src/nodes/registry.ts'; console.log('baseline',c().ok);p.OUTSIDE='M2';console.log('extra',c().ok,JSON.stringify(c().problems));delete p.SOURCE;console.log('missing',c().ok,JSON.stringify(c().problems))"
```

**关闭条件：**

```
baseline true
extra false ["OUTSIDE ..."]        ← 必须 false，且 problems 里点名 OUTSIDE
missing false ["SOURCE ..."]
```

## 3. E 项 · 监理修订可观察标准（重要）

### 3.1 验收方提给我的问题

> "若需按前缀内容而非显式键验收，应由监理修订可观察标准。"

**这个请求是对的。** 我 005 号写的标准——"两个不同的前缀键 → 两次出站请求体必须不同"——**对 Anthropic 是错的**。这是我的失误，我修正。

### 3.2 为什么原标准是错的

两家厂商的缓存机制不同：

| 厂商 | 缓存机制 | 能否用不透明字符串当键 |
| --- | --- | --- |
| **OpenAI** | 有 `prompt_cache_key` 字段，键是可传的标识 | ✅ 可以，键直接进请求体 |
| **Anthropic** | **内容寻址**：缓存的是 `cache_control` 标记的**内容块本身**，没有"传一个键"的概念 | ❌ **不能**。键只能决定"哪段内容进去"，不能自己出现在请求体里 |

所以 Anthropic 适配器在 `cachePrefixKey` 变化时请求体不变，**如果键只是个标签、system 内容恒定，那其实是正确行为**。

**但这个"如果"是关键**：如果键永远不参与内容构造，那它就是个死参数，前缀缓存根本没接入。所以标准要改，但**不能取消**。

### 3.3 修订后的标准（本轮起生效，替代 SG-SUP-004 §3.2 与 SG-SUP-005 §2.E 中的相关表述）

**统一前提：把 `cachePrefixKey` 升级为携带材料的对象。**

```
cachePrefix: {
  key: string,      // 缓存标识，如 'source:abc123:ch1:v4'
  text: string      // 实际进 system 前缀的原文片段
}
```

`key` 用于日志、指标、OpenAI 的字段；`text` 用于 Anthropic 的内容寻址。两者都由调用方从 `(sourceId, 章节范围, promptVersion)` 派生。

**三条可观察标准，两家都要满足：**

#### 标准 1 · 前缀材料变化 → 请求体必须变化（两家通用）

给两次调用不同的 `text`（例如不同章节的原文），**出站请求体必须不同**。

这是"前缀缓存真的接上了"的最低证明。如果换了教材内容请求体还一样，那缓存前缀根本不存在。

#### 标准 2 · 前缀材料相同 → 请求体必须相同（两家通用）

同样的 `text` 两次调用，请求体**必须完全一致**。否则缓存永远不会命中——这是反方向的证明，防止"每次请求都塞时间戳导致缓存失效"这类错误。

#### 标准 3 · 厂商各自的机制证据（分别验）

| 厂商 | 硬要求 | 在请求体里看什么 |
| --- | --- | --- |
| **OpenAI** | `key` 必须出现在请求体的缓存键字段中 | 请求体含 `prompt_cache_key: <key>`（或厂商等价字段），且值与传入的 `key` 一致 |
| **Anthropic** | `text` 必须作为 system 内容存在，且**最后一个 system 块带 `cache_control`** | 请求体内 `system` 数组里能读到 `text` 的子串，且存在 `cache_control: {type:"ephemeral"}`（或厂商当前等价写法） |

**关于 Anthropic 的 `key`：** 允许它**只用于**日志与指标，不要求进请求体。**但必须有一处可观测的用途**——不能是纯死参数。

### 3.4 复验命令（按新标准写，覆盖三条）

```powershell
node --input-type=module -e "import {createAnthropicProvider} from './apps/api/src/llm/providers/anthropic.ts';let bodies=[];const call=createAnthropicProvider({apiKey:'test',fetchImpl:async(u,o)=>{bodies.push(o.body);return Response.json({content:[{type:'text',text:'{}'}],model:'snapshot',usage:{input_tokens:3,output_tokens:1}})}});const P=[{key:'source:a:ch1:v1',text:'第一讲的原文'},{key:'source:a:ch1:v1',text:'第一讲的原文'},{key:'source:a:ch2:v1',text:'第二讲的原文'}];for(const p of P)await call({model:'alias',messages:[{role:'system',content:'lesson'}],cachePrefix:p});console.log('std1_diffText',bodies[0]!==bodies[2]);console.log('std2_sameText',bodies[0]===bodies[1]);console.log('std3_hasText',bodies[0].includes('第一讲'));console.log('std3_hasCacheControl',/'cache_control'.test(bodies[0]))"
```

**关闭条件（Anthropic）：**

```
std1_diffText true          ← 换章节，请求体必须变
std2_sameText true          ← 同章节，请求体必须一致
std3_hasText true           ← 原文真的进了请求体
std3_hasCacheControl true   ← 缓存断点真的标了
```

OpenAI 用同样三条 + `prompt_cache_key` 的存在性检查，命令自行组织，**必须贴出请求体原文**（脱敏后）。

### 3.5 附带要求

- 把新标准写进 `docs/architecture.md`，**说明两家机制的差异**，不要只写"实现了前缀缓存"
- 若某厂商当前 API 不支持 `cache_control` 或等价机制，**如实写进文档并标注"该厂商前缀缓存未接入"**，不许假装接了
