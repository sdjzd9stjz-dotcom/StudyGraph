## 2. 鉴权决定（回答你 §9 的问题）

### 2.1 结论

**M1 用最小 PAT，OAuth2 留到 M4。** 但**必须带 scope**。

### 2.2 理由

规格把 OAuth2 + PAT 放在「鉴权」一节，而「开放能力」（REST + SSE + MCP + PAT 鉴权 + 克隆）是 **M4** 的里程碑。M1 的鉴权只承担一件事：让 curl 带上身份。

提前上 OAuth2 会引入授权码流程、Redis 存 token、刷新逻辑——**M1 没有任何验收项能验证这些**，属于做了一件没人检查的事。

### 2.3 但有两个硬约束，M1 就要满足

**约束 A · scope 现在就建，不能先做无 scope 的粗 token**

`Scope` 枚举已成：`CANVAS_READ | CANVAS_WRITE | RUN_EXECUTE | PROBLEM_READ`。

如果 M1 的 token 没有 scope 概念，M4 验收「用只有 `canvas:read` 的 token 调 `node.run` 必须 403」时，要重构整个鉴权中间件。**现在建，成本是加一个参数；到 M4 建，成本是改所有路由。**

**M1 必须能证明 scope 是真的**，用这条验：

```bash
# 用只有 CANVAS_READ 的 token 调 POST /v1/canvases，必须 403 而不是 401 或 500
curl -sS -o /dev/null -w "%{http_code}\n" -X POST "$API_BASE_URL/v1/canvases" \
  -H "Authorization: Bearer $PAT_READONLY" -H "Content-Type: application/json" \
  -d '{"title":"should fail"}'
# 期望 403，body.error.code = INSUFFICIENT_SCOPE
```

**约束 B · token 只存哈希**

schema 里 `tokenHash @unique` 已留好。要求：

- 明文格式 `sg_pat_<32 字节 base64url>`，**只在创建时返回一次**
- 库里存 `sha256(明文)` 的十六进制
- `tokenPrefix` 存前 8 位（`sg_pat_` 之后），供 UI 展示与吊销
- 校验时按 hash 查表，**绝不存明文、绝不回显明文**

**这条我会实测**：查库确认 `tokenHash` 不是明文，且 `SELECT tokenHash FROM "PersonalAccessToken"` 的值与 seed 打印的明文对不上。

### 2.4 401 与 403 必须分清

| 情况 | 状态码 | errorCode |
| --- | --- | --- |
| 没有 `Authorization` 头 | 401 | `UNAUTHENTICATED` |
| token 不存在 | 401 | `UNAUTHENTICATED` |
| token 已 `revokedAt` | 401 | `TOKEN_REVOKED` |
| token 已 `expiresAt` | 401 | `TOKEN_EXPIRED` |
| token 有效但缺 scope | **403** | `INSUFFICIENT_SCOPE` |

**别把 403 写成 401。** 学生排查时，"你没权限"和"你没登录"是完全不同的两件事。

### 2.5 允许不做签发 UI

用 `scripts/seed-pat.ts`（或类似）插一条即可。但要求：

- 支持指定 scopes 与 userId
- 打印明文一次，并明确提示"只显示这一次"
- 脚本可重复执行（同名 token 先吊销旧的，或按 name 幂等）

## 3. M1 主体施工规格

### 3.1 技术基线

| 项 | 要求 |
| --- | --- |
| 后端 | Fastify，`apps/api`，端口 `API_PORT`（默认 3001） |
| 前端 | Next.js 14 App Router，`apps/web`，端口 `WEB_PORT`（默认 3000） |
| Prisma Client | 从 `packages/db` 导出，**单例**，不要每个路由 `new PrismaClient()` |
| 环境变量 | 启动时用 zod 校验，缺一个就退出（不留半配置运行） |
| 错误信封 | 全站统一 `{ error: { code, message, details? } }`，M1 起沿用 |

### 3.2 画布 CRUD

| 方法 | 路径 | scope | 成功 | 失败 |
| --- | --- | --- | --- | --- |
| `POST` | `/v1/canvases` | `CANVAS_WRITE` | 201 + `{ id, title, ownerId, createdAt }` | 400 参数非法 |
| `GET` | `/v1/canvases/:id` | `CANVAS_READ` | 200 + `{ id, title, nodes[], edges[] }` | 404 `CANVAS_NOT_FOUND` |
| `GET` | `/v1/canvases` | `CANVAS_READ` | 200 + 当前用户可见的画布列表 | — |
| `DELETE` | `/v1/canvases/:id` | `CANVAS_WRITE` | 204 | 404 / 403 |

**要求：**

- `ownerId` **从 token 的 UserCtx 取**，不接受 body 传入（否则能替别人建画布）
- `GET` 单画布时，非 owner 且非 `CanvasMember` 的调用者 → 404（不是 403，避免探测画布是否存在）
- `DELETE` 执行顺序按 `milestone-1.md` §2：**算 S3 key 清单 → 删库 → 删桶 → 失败只记 `orphanObjects`**
- M1 阶段桶可能为空（MinIO 未起），但代码路径必须在，且 `orphanObjects` 字段出现在响应或日志里

### 3.3 节点创建

| 方法 | 路径 | scope | 成功 |
| --- | --- | --- | --- |
| `POST` | `/v1/canvases/:canvasId/nodes` | `CANVAS_WRITE` | 201 + `{ id, type, status, posX, posY }` |
| `PATCH` | `/v1/nodes/:id` | `CANVAS_WRITE` | 200（改 `params` / `title` / 位置） |

**要求：**

- `type` 必须是 `NodeType` 的 17 个值之一，否则 400 `NODE_TYPE_INVALID`
- 新节点 `status` 默认 **`DRAFT`**，不是 `READY`
- `params` 默认 `{}`，且必须通过该 type 的 zod schema（M1 可以先只做 JSON 对象校验，但**不能跳过**）
- 跨画布创建（`canvasId` 属于别人）→ 404

### 3.4 边写入：**本轮验收核心**

```
POST /v1/canvases/:canvasId/edges
```

**校验顺序（写死在实现里，顺序即语义）：**

| # | 检查 | errorCode | HTTP |
| --- | --- | --- | --- |
| 1 | 画布存在 + 有 `CANVAS_WRITE` | `CANVAS_NOT_FOUND` / `INSUFFICIENT_SCOPE` | 404 / 403 |
| 2 | 两端节点存在且属于该画布 | `NODE_NOT_IN_CANVAS` | 400 |
| 3 | `fromNodeId !== toNodeId` | `EDGE_SELF_LOOP` | 400 |
| 4 | 端口名在该节点声明中存在 | `EDGE_PORT_NOT_FOUND` | 400 |
| 5 | 目标端口不是入口端口 | `EDGE_PORT_EXTERNAL` | 400 |
| 6 | 端口类型相同 | `EDGE_PORT_TYPE_MISMATCH` | 400 |
| 7 | 同 `(canvasId, from, to, kind)` 未重复 | `EDGE_DUPLICATE` | 409 |

> 第 3–6 条**必须调用 `packages/contracts` 的 `validateConnection()`**，不许在后端再写一份。前端也用同一个函数。**两份实现 = 迟早不一致。**

**`canvasId` 只从路径取**，body 里出现 `canvasId` 直接 400 `CANVAS_ID_IN_BODY`（防止客户端指定别人的画布）。

**数据库兜底必须仍然有效**（服务层绕过后仍拦得住）：

- `Edge.canvasId` + 复合外键 → 跨画布连边写不进去
- `edge_no_self_loop` CHECK → 自环写不进去

**并发要求**：两个相同请求同时到达，必须**一个 201 一个 409**，不能出现两行。这靠 `@@unique([canvasId, fromNodeId, toNodeId, kind])`，所以**不要先查后插**（先查后插在并发下必然漏）。正确做法是直接 insert 并捕获 `P2002` 转 409。

### 3.5 stale 标记（只标不跑）

| 方法 | 路径 | scope |
| --- | --- | --- |
| `POST` | `/v1/nodes/:id/mark-stale` | `CANVAS_WRITE` |

**要求：**

- 调 `collectDownstream(edges, nodeId)`（默认 `STALE_EDGE_KINDS`，只走 `DERIVED_FROM`）
- 把起点与全部下游置 `status = STALE`，写 `staleAt` / `staleReason`
- **绝不入队、绝不调用任何模型、绝不写 `Run` 表**

**验收方式（这条我会亲自跑）：**

```bash
BEFORE=$(docker exec studygraph-postgres psql -U studygraph -d studygraph -t -c 'SELECT count(*) FROM "Run";')
curl -X POST "$API_BASE_URL/v1/nodes/$A/mark-stale" -H "Authorization: Bearer $PAT"
AFTER=$(docker exec studygraph-postgres psql -U studygraph -d studygraph -t -c 'SELECT count(*) FROM "Run";')
# BEFORE == AFTER
```

同时查 `status`：A、B、C 三个节点都变 `STALE`（**孙节点也要变**，这是作弊库第 5 条"单层 stale"）。

### 3.6 图查询

| 方法 | 路径 |
| --- | --- |
| `GET` | `/v1/canvases/:id/graph?view=pipeline` |

**要求：**

- `view=pipeline` 必须实现
- `view=knowledge` / `view=method` → **501 `VIEW_NOT_IMPLEMENTED`**，附一句"计划 M3 / M5"
- **不许返回空数组冒充"没有数据"**。静默降级是本项目的红线

### 3.7 17 个占位卡片 + 拖拽

**要求：**

- 侧栏列出全部 17 种类型（中文名 + type），可拖到画布
- 卡片显示：type、状态色（`DRAFT` 灰 / `READY` 绿 / `STALE` **琥珀** / `ERROR` 红 / `RUNNING` 蓝）
- **stale 用琥珀色，红色只留给 error。** 这条是规格明文，用错描边颜色算 P2
- 拖拽结束后 `PATCH /v1/nodes/:id` 落库 `posX/posY`，刷新页面位置不变
- 卡片上的连接点来自 `NODE_PORTS`，入口端口（`external: true`）**渲染成"上传/粘贴槽"，不给连接点**

### 3.8 不做的事

- 不实现任何 executor（`apps/api/src/nodes/` 保持为空）
- 不做 SSE（M4）
- 不做 MCP（M4）
- 不做 knowledge / method 视图（M3 / M5）
- 不做 Yjs 协作（M1 只需单机拖拽落库）
