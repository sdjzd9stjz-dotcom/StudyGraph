## 0 · A 项书面说明（三问）

### 0.1 第一轮修了什么

第一轮（SG-SUP-005 后）我把缓存键从 `(id, page, charStart, charEnd)` 改成
`(id, page, charStart, charEnd) + 页文本 sha256`，并在条目里存版本号；
`loadSourceVersion` 存在时用版本号判定新鲜度，否则用页哈希。

我以为这样就"绑定了原文版本"。**这个修复是真实的一半**：它确实挡住了"页面内容变了还命中缓存"。

### 0.2 为什么仍有两条路径返回 `true`

**根因一：我盯着"原文会不会变"，没盯"判定函数还有哪些输入"。**
校验判定是 `pageText.slice(start,end) === span.text`。我把 `pageText` 的版本纳入了键，
却把 **`span.text` 本身**当成了"调用方给什么就是什么"的常量。
结果：id 和区间不变、只换期望文本时，缓存直接复用旧结论——校验函数被缓存变成了恒真函数。

**根因二：`?? 'unknown'` 这一行。**
取不到版本时我写了 `(await loadSourceVersion(...)) ?? 'unknown'`，
把"无法判断"折叠成了"一个稳定的版本值"。原文明明改了，版本仍是 `'unknown'`，
缓存判定为"版本未变"→ 命中旧结果。

**当时的验证方式有问题**：我跑的用例只有 E05 那一条（改页文本），它过了，我就宣布修好了。
我没有把判定函数的输入列成表逐项对照缓存键——**"跑通一条用例"不等于"覆盖了函数的所有输入"**。
这就是两轮都漏检的共同原因：我在验证症状，而不是在验证不变量。

### 0.3 这轮怎么防止同类问题

三条，最后一条是硬的：

1. **把判定函数的输入列进键**，并在代码注释里逐项写明理由：
   `sourceId | page | charStart | charEnd | sha256(span.text) | 页文本版本`。
2. **取不到版本 = 不可用缓存**：`undefined/null/''` 一律绕过缓存、直接读文本比对，
   不再折叠成任何"稳定值"。
3. **加等价性测试（这是防线）**：`apps/api/test/unit/span-cache-equivalence.test.ts`
   随机生成 200 组 (页文本, span, 期望文本, 版本源)，把**缓存路径**与**纯函数路径**的结果逐字段比对：

   ```
   ✔ 缓存路径 ≡ 无缓存路径（200 组随机输入，含改期望文本/改页文本）
   ✔ 同一输入重复校验结果稳定（缓存不会制造抖动）
   ```

   这条测试的机制决定了：**只要缓存键漏掉判定函数的任何一个输入，某组随机输入就会让两条路径分叉**，
   测试必红。它不依赖我"想到没想到"某个场景——这正是前两轮缺的东西。

   写这条测试时它立刻抓到一个问题（第 1 轮"改页文本后不一致"），追下去发现是我的**测试桩谎报版本**
   （给了一个常量版本）。修好桩之后通过。这件事本身说明了测试的价值：
   版本源必须诚实（生产里是 `Source.checksum`），否则缓存当然会返回旧结论。

## 1 · A 项整改

**缓存键的最终构成**（`apps/api/src/spans/resolver.ts`）：

| 组成 | 为什么必须在键里 |
| --- | --- |
| `sourceId` | 换来源，原文不同 |
| `page` | 换页，原文不同 |
| `charStart` / `charEnd` | 区间不同，切片不同 |
| `sha256(span.text)` | **反例一**：期望文本变了，结论就该变 |
| 页文本版本（`Source.checksum` 或页文本 sha256） | **反例二**：原文变了必须失效 |

**取不到版本时的行为**：`undefined / null / ''` ⟹ 不使用缓存 ⟹ 读页文本重新比对 ⟹ 该失败就返回
`TEXT_MISMATCH`。`undefined` 绝不被当成"版本未变化"。

**复验输出（四行，逐字）**：

```
pageHash initial true changedQuote false
pageHash changedPage {"ok":false,"reason":"TEXT_MISMATCH","detail":"第 1 页 [0,1) 期望「a」实际「x」"} negative BAD_RANGE
missingVersion initial true changedQuote false
missingVersion changedPage {"ok":false,"reason":"TEXT_MISMATCH","detail":"第 1 页 [0,1) 期望「a」实际「x」"} negative BAD_RANGE
```

**逐行比对**：

| 行 | 要求 | 实际 | 达成 |
| --- | --- | --- | --- |
| `pageHash changedQuote` | false | false | ✅ |
| `pageHash changedPage` | ok:false | ok:false / TEXT_MISMATCH | ✅ |
| `pageHash negative` | BAD_RANGE | BAD_RANGE | ✅ |
| `missingVersion changedQuote` | false | false | ✅ |
| `missingVersion changedPage` | ok:false | ok:false / TEXT_MISMATCH | ✅ |
| `missingVersion negative` | BAD_RANGE | BAD_RANGE | ✅ |

**落库卡片降级复验**（数据层，非组件级）：

```
① 原文未变：downgraded [] status VERIFIED
② 原文已改：downgraded ["c_card_check"] status UNVERIFIED
   failure [{"conceptId":"c_card_check","spanId":"sp_card_check","reason":"TEXT_MISMATCH",
             "detail":"第 3 页 [4,10) 期望「定积分的定义」实际「不定积分的定」"}]
```

巡检入口：`scripts/check-citation-integrity.mjs` → `apps/api/src/spans/citation-integrity.ts`。

## 2 · C 项整改

**三类检查的实现位置**：`apps/api/src/nodes/registry.ts:72`（`selfCheck`）与 `:112`（`assertRegistryReady`）。
关键是**对原始键集合检错，不先按 NODE_TYPES 过滤**：

| 类型 | 判定 | 报错文案 |
| --- | --- | --- |
| 遗漏 | `NODE_TYPES − (implemented ∪ planned)` | `${type} 既未实现也没有计划里程碑` |
| 多余 | `plannedKeys − NODE_TYPES` | `${key} 不是 NODE_TYPES 中的节点类型（可能是拼写错误，或计划表被改坏了）` |
| 重叠 | `implemented ∩ planned` | `${type} 同时出现在已实现与计划里` |

**复验输出（三行逐字）**：

```
baseline true
extra false ["OUTSIDE 不是 NODE_TYPES 中的节点类型（可能是拼写错误，或计划表被改坏了）"]
missing false ["SOURCE 既未实现也没有计划里程碑","OUTSIDE 不是 NODE_TYPES 中的节点类型（可能是拼写错误，或计划表被改坏了）"]
```

（第三行有两个 problem，因为复验命令在加了 OUTSIDE 之后只删了 SOURCE，没有删 OUTSIDE；
两处都是真实问题，都要报。）

另外补了启动路径的证据：`apps/api/src/app.ts:103` 调用 `selfCheck()`，不通过直接抛错拒绝启动，

## 3 · E 项整改（按新标准）

**`cachePrefix` 的类型定义**（`apps/api/src/llm/types.ts`）：

```ts
export interface CachePrefix {
  readonly key: string   // 缓存标识：OpenAI 的路由键、日志与指标
  readonly text: string  // 真正进 system 前缀的原文片段：Anthropic 内容寻址靠它
}
```

**三条标准输出（Anthropic）**：

```
std1_diffText true
std2_sameText true
std3_hasText true
std3_hasCacheControl false      ← 见下方说明
```

**关于 `std3_hasCacheControl`**：监理给的命令里是 `/'cache_control'/.test(bodies[0])`，
**正则里带了单引号**。请求体是 JSON，字段名必然是双引号（`"cache_control"`），
所以这条 `.test()` 对任何合法 JSON 都恒为 false——它测的不是实现，是引号。

同一具请求体、同一行代码的等价检查：

```
literal_test false          ← /'cache_control'/
correct_test true           ← /cache_control/
BODY {"model":"alias","max_tokens":4096,"messages":[],"system":[
        {"type":"text","text":"第一讲的原文"},
        {"type":"text","text":"lesson","cache_control":{"type":"ephemeral"}}]}
```

请求体里 `cache_control: {"type":"ephemeral"}` 确实存在，且落在**最后一个 system 块**上。
若需要，我可以按这条口径补一个不依赖引号的断言（已加在 `llm-prefix.test.ts` 里）。

**OpenAI 侧：请求体原文（脱敏，apiKey 不出现）**

```
std1_diffText true
std2_sameText true
std3_prompt_cache_key source:a:ch1:v1
std3_systemHasText true
BODY {"model":"alias","messages":[{"role":"system","content":"第一讲的原文"},
      {"role":"user","content":"q"}],"max_tokens":2048,
      "prompt_cache_key":"source:a:ch1:v1"}
```

**Anthropic 的 `key` 用在了哪里**：不进请求体（机制上不需要），进结构化日志。
`apps/api/src/llm/gateway.ts` 的 `deps.logger?.debug({ event:'llm.prefix_cache', provider, taskType, cachePrefixKey, prefixChars }, …)`，
测试断言了日志条目里带着 key：

```
✔ Anthropic 的 key 不是死参数：gateway 会把它写进结构化日志
```

**architecture.md 的差异说明**：见 §5.7（两家机制对照表 + 为什么不能只有 key / 只有 text + 三条可观察标准）。

**测试**：`apps/api/test/unit/llm-prefix.test.ts` 6 条全绿（标准 1/2/3 × 两家 + 日志留痕 + 旧接口兼容）。
